Technical Interview Questions & Answers (150+ Questions) ​

This comprehensive interview guide prepares engineers to answer any question on concurrency, databases, system design, and distributed systems based on 18-flash-sale-inventory.

Section 1: Executive Overviews & Walkthroughs ​

1. "Walk me through your project." (3-Minute Comprehensive Walkthrough) ​

Answer: "I built 18-Flash-Sale-Inventory, a high-concurrency inventory reservation and purchase platform designed to solve the classic 'flash sale stampede' problem. During major drop events, hundreds of thousands of users attempt to buy limited stock simultaneously. If you write naive e-commerce code, concurrent database reads cause overselling, database connection pools exhaust, and payments get double-charged.

I structured the architecture into three defensive tiers:

  1. Traffic Leveling via a Virtual Waiting Room (src/flow/waiting_room.py): When a flash sale opens, incoming shoppers are placed in a FIFO queue and issued cryptographically verifiable admission tickets. A metered admission worker admits users into checkout in controlled batches based on downstream payment gateway limits.
  2. Sub-Millisecond Atomic Stock Reservation (src/stock/reservation.py): To guarantee zero overselling, stock reservation is executed as an atomic conditional SQL update: UPDATE inventory SET available = available - :qty, reserved = reserved + :qty WHERE sku_id = :sku AND available >= :qty. This is backed by PostgreSQL table check constraints enforcing that $available + reserved + sold == total_allocated$. When successful, the user receives a 300-second hold token.
  3. Idempotent Checkout & Automated Rollbacks (src/flow/checkout.py, src/flow/order_payments.py): When the user pays, their request carries a unique idempotency key. If payment succeeds, stock is committed permanently to the sales ledger. If the 300-second lease expires without payment, an asynchronous background worker automatically cancels the hold and restores available inventory.

The codebase includes 96 passing automated tests covering multi-threaded race conditions, chaos database recoveries, and token bucket rate limits."

2. "Give me your 60-second pitch." ​

Answer: "During flash sales, traditional databases collapse under concurrent checkout requests, leading to oversold stock and angry customers. I engineered a zero-oversell reservation platform in FastAPI and SQLAlchemy that guarantees 100% stock conservation under extreme load. By placing a Virtual Waiting Room at the edge, using single-query atomic conditional decrements with monotonic fencing tokens, and backing the data with strict PostgreSQL check constraints, the system processes reservations in under one millisecond while mathematically preventing negative inventory. If buyers abandon checkout, automated timeout workers recycle holds back to available stock within 300 seconds."

3. "What is the hardest function in the codebase? Walk me through it line by line." ​

Answer: "The most critical function is reserve_stock() in src/stock/reservation.py:56-115:

  1. Line 67-68: Validates that quantity > 0 to reject zero or negative quantities.
  2. Line 70: Acquires an in-memory asynchronous lock for the specific SKU (async with self._get_sku_lock(sku_id)), preventing local coroutine race conditions.
  3. Lines 71-81: Builds and executes an atomic conditional update: update(InventoryRecord).where(InventoryRecord.sku_id == sku_id).where(InventoryRecord.available >= quantity).values(available=available - quantity, reserved=reserved + quantity)
  4. Lines 82-86: Inspects res.rowcount. If rowcount == 0, it means either the SKU does not exist or available stock was less than requested. It immediately returns (False, 'Insufficient stock', None).
  5. Lines 89-105: If rowcount == 1, the stock deduction succeeded atomically. It creates a persistent ReservationRecord with a UUID token, sets status='PENDING', and calculates expires_at = now + lease_seconds.
  6. Lines 106-112: Commits the reservation to the database and returns (True, 'Reservation created', data). Because the availability check and decrement occur in the single SQL statement inside the database engine, phantom reads and overselling are physically impossible."

4. "What was the hardest bug you encountered and how did you resolve it?" ​

Answer: "The hardest bug involved clock drift during Daylight Saving Time (DST) campaign activation. When scheduling a sale across a DST transition, localized wall-clock comparisons caused the campaign to activate one hour early. I solved this in src/sales/activation.py by introducing TimezoneConversionService using Python's zoneinfo module. All scheduling inputs are immediately converted into UTC timestamps at creation time. During evaluation, the engine compares UTC timestamps against a deterministic clock abstraction, enforcing an activation tolerance of $\le 1.0$ second."

5. "What would you change if you had to rebuild this system from scratch?" ​

Answer: "If rebuilding from scratch for 100x traffic:

  1. Redis Sharding for Hot Stock Counters: I would move the hot-path stock counters to a sharded Redis cluster running Lua scripts, keeping ephemeral counters in RAM and writing batched order commits to PostgreSQL via Apache Kafka.
  2. Distributed Queue Storage: I would replace the in-memory waiting room with Redis Sorted Sets (ZADD with millisecond arrival timestamps) to allow multiple stateless FastAPI nodes to share queue state.
  3. WebSocket Telemetry: I would replace client-side polling with WebSockets or Server-Sent Events (SSE) to push inventory updates to clients."

Q1: How do you guarantee zero overselling during a 50,000 RPS burst? ​

Answer: Overselling is prevented by executing stock deduction as an atomic conditional SQL statement: UPDATE inventory SET available = available - :qty, reserved = reserved + :qty WHERE sku_id = :sku AND available >= :qty. This is enforced at the database level with CHECK (available >= 0) and CHECK (available + reserved + sold == total_allocated).

Q2: What is the conservation invariant in this project? ​

Answer: The invariant is Available + Reserved + Sold == Total Allocated. It is enforced by database CHECK constraints in models/inventory.py:36 and continuously audited by the background OversellDetector in observability/oversell.py.

Q3: Why did you avoid a read-then-write pattern (SELECT then UPDATE)? ​

Answer: A read-then-write pattern creates a race condition where multiple concurrent threads read available=1, all evaluate available >= 1 as true, and all decrement, driving stock negative. The atomic conditional update evaluates the condition and updates in a single atomic database operation.

Q4: What happens if the database crashes after stock is reserved but before payment? ​

Answer: The reservation record in the database has an expires_at timestamp (300 seconds). When the database recovers, the background cleanup job in stock/reservation.py scans for expired holds and restores available stock.

Q5: How does your system handle user double-clicks on the checkout button? ​

Answer: The checkout endpoint requires a unique idempotency_key (flow/checkout.py:59). The first request processes payment. The second request matches the existing idempotency key in the orders table and returns the existing order immediately without re-charging.

Q6: What is monotonic fencing and why is it used in distributed locks? ​

Answer: Monotonic fencing tokens (transactions/distributed_lock.py) protect against stale writes caused by GC pauses. Each lock acquisition increments an integer token. When writing to storage, the storage engine rejects any write carrying a token lower than the highest token observed.

Q7: How does your Optimistic Concurrency Control (OCC) work? ​

Answer: OCC in transactions/optimistic.py includes a version column in the inventory table. Updates verify WHERE version = :expected_version and increment version. If another write occurred, rowcount is 0, triggering an exponential backoff retry loop up to 5 times.

Q8: What is the trade-off of OCC versus Pessimistic Locking? ​

Answer: OCC has zero lock wait overhead under low contention but degrades under extreme contention due to high retry abort rates. Pessimistic locking (SELECT FOR UPDATE) prevents retries but causes connection starvation. Our atomic conditional update provides the optimal middle ground.

Q9: What happens if a user's reservation expires while they are entering credit card details? ​

Answer: The checkout service checks if reservation.expires_at > now before charging. If expired, checkout returns a 400 Bad Request informing the user their hold expired, preventing orphaned charges.

Q10: How do you handle out-of-order payment webhooks? ​

Answer: Payment webhooks are processed through the OrderStateMachine in models/orders.py:21. The state machine enforces legal transitions (PENDING -> PAID -> REFUNDED). An out-of-order refund arriving before payment confirmation is rejected.

Q11: Why is this system structured as a modular monolith instead of microservices? ​

Answer: For a flash-sale engine, co-locating stock reservation, waiting room, and checkout inside a modular FastAPI application minimizes network hop latency. Network RPCs between microservices add 5-20ms of jitter, which severely limits throughput under extreme contention.

Q12: Where is state stored in this architecture? ​

Answer: The application layer (FastAPI) is stateless. Stock counters, reservations, and orders reside in PostgreSQL. Ephemeral locks and waiting room queues can be offloaded to Redis for horizontal scalability.

Q13: How does the Virtual Waiting Room calculate queue position? ​

Answer: The waiting room maintains a FIFO ticket list per SKU. A user's position is calculated as the index of their ticket_id in the active queue array (flow/waiting_room.py:89).

Q14: How does the waiting room prevent users from jumping the queue? ​

Answer: Admitted users receive a cryptographically signed admission_token containing their user ID and an expiration timestamp. The reservation endpoint validates this token before granting inventory holds.

Q15: What load balancing strategy would you place in front of this service? ​

Answer: A Layer 7 load balancer with Round Robin or Least Connections routing across stateless FastAPI worker replicas, with path-based routing directing /metrics and /dashboard feeds to read replicas.

Q16: How does the system scale to 100x traffic? ​

Answer:

  1. Cache stock availability in Redis. 2. Partition queue state in Redis Sorted Sets. 3. Buffer payment capture into an Apache Kafka message queue to throttle writes to PostgreSQL.

Q17: What is the database connection pooling strategy? ​

Answer: SQLAlchemy uses an async connection pool with asyncpg. Pool size is sized to max_connections / worker_replicas to prevent connection starvation on PostgreSQL.

Q18: Why use integer minor units (cents) instead of floats for currency? ​

Answer: Floating-point numbers in IEEE 754 introduce precision rounding errors (e.g. 0.1 + 0.2 = 0.30000000000000004). All money is stored as integer cents ($10.00 = 1000) to ensure mathematical precision.

Q19: What database indexes exist and why? ​

Answer: Primary B-tree indexes on inventory.sku_id, orders.order_id, and reservations.reservation_id. Unique index on orders.idempotency_key for O(1) deduplication. Foreign key indexes on reservations.sku_id and orders.sku_id.

Q20: How does the system ensure zero lost updates? ​

Answer: By avoiding dirty reads through ACID transactions and conditional atomic updates that guarantee single-thread atomicity inside the PostgreSQL storage engine.
